## When a statistical model hits physical memory

Over the past decade the data in large-scale assessment have grown by two orders of magnitude: national monitoring programmes routinely have hundreds of thousands of test-takers, and some census-style projects reach a million. Yet the mainstream algorithm for IRT estimation (marginal maximum likelihood within the EM framework) has an Achilles' heel that swells with scale — **the posterior matrix in the E-step**.

A quick refresher on the algorithm. In each MML-EM iteration:

- **E-step**: for every test-taker n and every quadrature node q, compute the posterior probability P(θ_q | X_n) — an **N × Q matrix**.
- **M-step**: update the item parameters using expected counts weighted by those posteriors.

A unidimensional model has Q ≈ 40 nodes; with N = 1 million, the matrix holds 4 × 10⁷ double-precision numbers, about 320 MB — manageable. But **in multidimensional models the number of nodes grows exponentially with the number of dimensions**: 15 nodes per dimension and 3 dimensions make 3,375 nodes, and N × Q balloons to 3.4 × 10⁹ numbers — **27 GB**. With 4 dimensions it shoots up to 400 GB. The problem is not that it runs slowly; it simply doesn't fit in memory. Conventional implementations (which keep the entire posterior matrix in memory) all hit the wall here.

## Four engineering routes

Our solution in our own estimation engine, IRTC (published on CRAN, with open source code on GitHub), combines four routes:

**1. Streaming posterior computation (the root fix).**
The key observation: the M-step doesn't need the posterior matrix itself, only **a few aggregates** of it (the expected number of people at each node, the expected number of correct answers, and so on). These aggregates can be **accumulated block by block over test-takers**: take a block of people → compute its posteriors → add them to the accumulators → discard the posteriors → next block. Peak memory drops from O(N × Q) to O(block size × Q), **decoupled from the total sample size**. A million respondents use the same memory as a hundred thousand; there are just more blocks to compute. This is the core of "a million cases on an ordinary workstation".

**2. Dimension decomposition (fighting the exponential).**
Under a between-item multidimensional structure (each item loads on only one dimension), the likelihood can be decomposed given the correlation structure between dimensions, avoiding integration over the full D-dimensional grid — bringing "exponential" back down to "polynomial". And this structure is exactly the norm in large-scale assessment (almost every scale reported by dimension has a between-item multidimensional structure).

**3. C++ and parallelism (fighting the constant).**
Blocks of test-takers are naturally independent, so the E-step parallelises perfectly. The core is implemented in C++ (Rcpp/RcppArmadillo), with multithreaded blocks and vectorised likelihood computations. R is only the interface layer: users get an ordinary R package, while the engine runs at compiled speed.

**4. Numerical details (fighting the iteration count).**
Analytic gradients (rather than numerical differences) plus a hybrid Newton-type M-step reduce the number of iterations. Pruning quadrature nodes (skipping nodes whose posterior mass is negligible) speeds things up further — but that is **an approximation**, so IRTC makes it an explicit option, checks the pruning error empirically layer by layer, and reports it. **The default path is always exact computation: performance optimisation must never silently change the statistical target.** That is the bottom line.

## Validation: fast but wrong is worth nothing

The biggest risk with a large-scale engine is not slowness but **being wrong without anyone noticing**. Our validation matrix has three layers:

1. **Agreement with reference implementations**: on conventionally sized data, parameter estimates agree with mature implementations (mirt/TAM) within tolerance.
2. **Simulation recovery**: generate data from known true parameters → estimate → check bias and coverage.
3. **Path equivalence**: the grid engine and the streaming engine give the same results on the same data (blocking only rearranges the computation; it doesn't change the mathematics).

All of these are built into automated tests that rerun with every code change. **When statistical software computes something wrong, it doesn't crash — it just hands you a wrong number. Tests are the only line of defence.**

## Three general lessons beyond this tool

1. **Ask about the aggregates before you think about the matrix**: in large-scale statistical computing, the first question should be "what does the downstream step actually need from this big object?" Anything that can be aggregated in a stream should never be held in memory as a whole. The principle applies to engineering any EM-type or MCMC-type algorithm.
2. **Make approximations an explicit contract**: every speed-up approximation should be switchable, auditable, and accompanied by an error report. "Exact by default, acceleration by choice" means users always know what they are computing.
3. **At the end of every performance problem lies a statistical one**: once memory and speed have been optimised, success still depends on whether the model is specified correctly, the convergence criteria are strict enough, and the parameters are identifiable. Engineering serves statistics, not the other way round.
