# A28 · What Makes Statistical Software Trustworthy: Automated Testing and "Honest Failure"

> Engineering quality track. Sets out a distinctive philosophy; suitable for an adapted submission to Capital of Statistics.

## An uncomfortable fact

Errors in statistical software almost never show up as crashes. They show up as **a perfectly normal-looking number that is quietly wrong.**

A weight applied one time too few, missing values treated as zeros, a convergence criterion that is too loose, the wrong formula under some edge condition — these errors throw no exceptions and pop up no dialogs. They slip into reports, papers, and the evidence behind policy, hidden behind the decimal point. Users have no way of noticing: who can tell by eye that "0.437" should have been "0.512"?

So "can this statistical tool be trusted?" is a question that demands a serious answer. This article offers a practical framework for answering it. It is both the internal standard we apply when developing our own tools (such as the open-source IRTC) and a checklist you can use directly to evaluate any statistical software — including the code accompanying a paper you are reviewing.

## Four pillars of trustworthiness

### Pillar 1: Benchmark validation — check against known answers

Method: compare, within tolerance, against hand-worked textbook examples, the accepted output for classic datasets, and estimates of the same model from mature software.
This is the simplest and most effective check. **An implementation that has never been compared against an outside answer is correct only in its author's opinion.** For users, this means looking for benchmark records in the documentation or tests; for developers, at least one cross-implementation benchmark before any model goes live.

### Pillar 2: Simulation recovery — the gold-standard test of statistical correctness

Statistical methods allow a luxurious kind of self-check: **you can make your own data**. Generate simulated data from known true parameters → estimate them with the software → check that the estimates are distributed around the true values in the right way (bias tending to zero, calibrated standard errors, confidence intervals with their nominal coverage).
This check is stronger than benchmarking: a benchmark only proves "it agrees with others", while simulation recovery proves "it is statistically correct under the model's assumptions". It also answers, as a by-product, "at what sample size does this method become stable?" — the empirical source of the "recommended sample size" in the documentation.

### Pillar 3: Edge cases and foolproofing — errors should die at the door

Real data inevitably bring edge cases: empty categories, items everyone gets right or wrong, constant variables, a single record, invalid codes. Trustworthy software has a defined behaviour for every one of them: **either handle it correctly or fail with a clear error** — the worst behaviour is to silently return a number.
In testing terms this means a set of edge-case tests; in design terms, input validation plus plain-language error messages. When evaluating a package, feed it bad data on purpose and watch how it reacts — those five minutes tell you more than ten pages of marketing.

### Pillar 4: Regression protection — never fall into a fixed hole again

Every fixed bug becomes a permanent test, and every code change automatically reruns the full test suite (CI, continuous integration). This ensures the software's trustworthiness **never decreases** — without regression protection, every "optimisation" is a roll of the dice.
For evaluators: whether a GitHub repository has a tests directory and a CI badge is the most visible sign of engineering discipline.

## A higher standard: "honest failure"

Above the four pillars sits a design philosophy we call honest failure:

- **Make the limits of capability explicit**: when something can't be computed (structural infeasibility, non-convergence, a sample too small to support the specification), say clearly "this can't be computed" and why — never silently degrade or output a best guess.
- **Approximations require informed consent**: every option that trades accuracy for speed (pruning quadrature nodes, approximate algorithms) should be off by default, switched on explicitly, and accompanied by an error-check report — users always know whether they have an exact or an approximate solution.
- **Pass uncertainty on truthfully**: don't quietly narrow a confidence interval that should be wide, and don't bury a convergence warning in a log.

We have all seen the opposite of this philosophy: software that, in the name of "ease of use", produces a result for any input and never raises an alarm. **In the short term it looks like good user experience; in the long term it shifts all the methodological risk onto the people least able to recognise it.**

## Action lists for three kinds of reader

**Software users**: prefer tools with tests, CI, and benchmark records; cross-check key results once with an independent implementation.

**Code authors (researchers)**: write at least three kinds of assertion for your analysis scripts — data assertions (units, ranges, sample sizes conserved), known-answer anchors, and checks that edge cases raise errors. testthat or ten lines of `stopifnot` will do; having them matters more than perfection.

**Buyers**: write "deliverables include automated tests" into the contract. Especially where a program will run in your environment for a long time (as in "data never leave the building" delivery), the tests are a remote guarantee of quality — they are the default in everything we deliver, and they should be your default requirement of any supplier.

The trustworthiness of statistical software has never been a function of its author's reputation or a polished interface; it is a function of this process. Where the process exists, trust follows.
