# A22 · Building an R Package from Scratch to Release: How a Statistical Tool Is Born

> In-depth companion to Q25. R tools track; suitable for an adapted submission to Capital of Statistics.

## Why researchers should know how to write packages

Every piece of analysis code you've written that you'll "use again next time" faces the same three possible fates: rotting in some project folder; being copied and pasted into seven slightly different variants; or being packaged into a documented, tested, installable tool.

The third path costs less than most people think (modern tooling has automated all the mechanical work), and its returns compound: **a package is the executable form of a research method**. It makes your method installable, verifiable, and citable, and it forces you to think your interface and assumptions through. Below is the complete route from nothing to release, with practical notes from open-sourcing our IRTC package.

## Stage 1: Skeleton and a minimal working version (one afternoon)

```r
usethis::create_package("mytool")   # generate the standard skeleton
usethis::use_mit_license()          # choose a licence
usethis::use_git()                  # version control from day one
```

Move your functions into `R/`, write roxygen2 comments above each one (`@param`, `@return`, `@examples`, `@export`), and then:

```r
devtools::document()   # comments → help pages
devtools::load_all()   # load for debugging
devtools::check()      # full check-up: aim for 0 errors, 0 warnings
```

`check()` is a good teacher: fix whatever it complains about, and by the time you're done you'll understand how packages work. You need just one reference book throughout: Wickham's *R Packages* (free online).

## Stage 2: Make it trustworthy (the stage that decides success)

**Tests — the lifeline of statistical software.**
The frightening thing about statistical code is that when it computes something wrong, it doesn't throw an error; it quietly returns a wrong number. Start with `usethis::use_testthat()`. Test strategies, in order of importance:

1. **Correctness anchors**: compare against known answers (small examples worked by hand, textbook examples, results from mature software).
2. **Simulation recovery**: generate data from known true parameters → estimate → assert that the bias is within tolerance (the gold-standard test for statistical methods).
3. **Edge cases and foolproofing**: empty data, all missing, a single row, invalid arguments — each should produce **a clear error message**, not a mysterious crash.
4. **Regression tests**: turn every bug you fix into a test, so you never fall into the same hole twice.

Rule of thumb: you pass only when there is at least as much test code as functional code. In IRTC's automated tests, simulation recovery and cross-implementation comparisons make up the majority — that is where our confidence that "the engine computes correctly" comes from.

**A philosophy of error messages.** When the input is invalid, report the error at the point of failure in plain language ("resp contains negative values; the response matrix must contain non-negative integers") rather than leaving users to dig through a 20-level call stack. **Explicitly refuse** anything outside the method's limits, and never silently return dubious results — "failing honestly" is a virtue in statistical software.

**Vignettes.** Function documentation answers "how do I call this?"; a vignette answers "in what situation, with what complete workflow, and how do I interpret the results?" A good vignette often travels further than the package itself.

## Stage 3: Performance (if your field needs it)

Squeeze everything out of R first: vectorise, avoid growing objects inside loops, use data.table. If that still isn't enough, bring in Rcpp:

```r
usethis::use_rcpp_armadillo()
```

Move the bottleneck functions (usually tight loops such as likelihood computations) down into C++ and keep only the interface in R. That is exactly IRTC's architecture: the estimation engine is entirely C++ (including multithreading and streaming memory management), while users still work with ordinary R functions. **The principle: profile before you optimise (the profvis package); optimising by gut feeling is wrong nine times out of ten.**

## Stage 4: Release

**Releasing on GitHub (doable in a day)**: push to a repository + a README (one paragraph explaining what problem it solves + the install command + a minimal example) + CI with GitHub Actions (`usethis::use_github_action("check-standard")`, automatic checks on several platforms). Users can then install it with `remotes::install_github()`. That is already a proper open-source release.

**Submitting to CRAN (an optional next step)**: the value lies in a trusted endorsement and the reach of `install.packages()`. The extra homework: policy compliance (time limits on running examples, not writing to the user's disk, complete documentation), checks on several platforms (`devtools::check_win_devel()`, rhub), and a `cran-comments.md` cover letter. Submissions are reviewed by people, and being sent back the first time is normal — fix each point and resubmit. The right attitude: the reviewers are helping you reach release quality.

**Citation and attribution**: add an `inst/CITATION` file so that when users cite the package in papers, the authors and source come with it automatically — that is where the long-term payoff of an academic tool comes from.

## Time budget for reference

A minimal working version: 1 day. A trustworthy version with tests and a vignette: 1–2 weeks (in spare time). Polishing to CRAN standard: another 1–2 weeks. Compared with developing the method itself, packaging costs next to nothing, yet it determines the method's **radius of survival**: a script in a folder won't outlive the project, while an open-source package with tests and documentation can live for many years.
