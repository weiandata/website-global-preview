## A common deadlock

A great many research institutes, government departments, and public institutions in China hold high-value survey data — living-standards surveys, literacy monitoring, sector censuses. These datasets have two things in common: **the analysis requires specialist expertise** (measurement modelling, sample weighting, equating and linking are all specialised methodology), and **the data themselves cannot leave the building** (they involve personal information or sensitive domains, and the regulatory red lines are clear).

The result is a deadlock: inside, there aren't enough people or enough methodological depth; outside, the experts have the skills but may not touch the data. The three usual "solutions" each come at a price:

- **Struggle through it in-house**: you are never sure of the methodological quality, and the results can't withstand scrutiny once published.
- **Bend the rules and hand the data over**: the compliance risk is huge, and a single leak is disqualifying.
- **Give up on in-depth analysis**: data collected at a cost of millions yield only a few tables of descriptive statistics — a waste.

There is in fact a fourth way, and it has been working in practice for years: **bring the tools in, rather than sending the data out.**

## The core of the model: separate the tools from the data

Break "analysis services" down and ask what an outside expert actually contributes that nobody else can. It is **methodological design and its implementation in code** — not the act of handling the data personally. Based on that insight, delivery can be restructured as follows:

**Step 1: Develop against the structure, not the data.**
The client provides only a data dictionary (list of variables, types, value ranges, a description of the sampling frame) — if necessary with a few thoroughly de-identified sample records. From this, the contractor **generates simulated data with exactly the same structure**: the same variables, the same codes, the same orders of magnitude, but every single value is fake.

**Step 2: Do all development and testing on the simulated data.**
Cleaning, modelling, weighting, report output — the entire analysis pipeline is developed, debugged, and run end to end on simulated data. Automated tests come with it, asserting the "facts that must hold" — sample sizes, sums of weights, permissible parameter ranges — so the program doesn't merely run, it computes correctly.

**Step 3: The program goes in; the client runs it.**
The contractor delivers a complete analysis program plus an operating manual. The client's own staff run it on the real data inside their intranet or an isolated environment and produce **aggregate-level results** (parameter tables, statistical reports, charts).

**Step 4: Iterate remotely on de-identified output.**
Real data always contain situations the simulated data did not anticipate (new missing-data patterns, extreme values, coding exceptions). A key design principle is that the program turns these situations into **diagnostic logs that contain no individual-level data**. The contractor reads the logs and the aggregate output, locates the problem, and ships a new version.

Looking back over the whole process: the outside team never sees a single real record. **The physical boundary of the data and the responsibility for managing them do not change at all.** This is not "safer outsourcing"; it removes the need for data to leave the building in the first place.

## What the model means for the client

**Compliance**: "The contractor does not access raw data" can be written straight into the contract — a far stronger guarantee than any non-disclosure agreement. An NDA governs "you may not leak data you hold"; this model means "you never hold the data at all".

**Assets**: traditional outsourcing buys a report (a one-off consumable). This model buys **a reusable program**. When next year's data arrive, you rerun it; when a definition changes slightly, you change a configuration setting. For monitoring programmes with repeated rounds, the marginal cost drops sharply from the second year, and the institution builds up the ability to run the analysis itself.

**Quality**: the model actually forces higher engineering standards. Because the program has to run in an environment the contractor cannot see, operated by people who did not write it, it must be reproducible (fixed seeds and versions; the same input always gives the same output), self-checking (automated tests built in), and honest about errors (it says explicitly when it meets something it cannot handle, rather than silently producing dubious results). In other words, **the "data never leave" constraint eliminates cottage-industry delivery where "it ran once" counts as done** — loose collections of scripts simply cannot survive in this model.

## Where it fits, and where it needs adapting

Good fit: repetitive or standardised tasks with clear analytical goals (modelling and weighting for annual monitoring, routine reports), and one-off in-depth analyses with well-defined methods.

Needs adapting: highly exploratory analysis (you don't know what's in the data and decide the direction as you go). When delivering a program alone isn't enough, it can be combined with **on-site work** (contractor staff work at the client's premises on the client's equipment, and the results stay with the client) or a **secure room / remote desktop** (controlled access to an isolated environment). Once the exploration has converged, return to program delivery to make the results permanent. The three levels of isolation can be matched to the sensitivity of the data.

## A checklist for institutions choosing a provider

1. The contract states that "the contractor does not access raw data" and lists the deliverables (program, tests, manual, codebook).
2. The acceptance criterion is "client staff can run the whole workflow independently by following the manual".
3. Require automated tests and version records in the program — they are the lifeline for troubleshooting inside a closed network.
4. Allow time for 2–3 rounds of "feedback from real data → new version" (simulated data cannot anticipate everything).
5. When assessing a provider, look at publicly verifiable engineering work (open-source projects, technical documentation). Program delivery demands far more engineering capability from the provider than traditional consulting does.
