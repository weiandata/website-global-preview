# A23 · A Reproducible Research Workflow: The Complete Recipe with R + Git + Automated Tests

> In-depth companion to Q24. Engineering quality track.

## A hidden illness in our industry

"The chart from three months ago won't run any more." "I switched computers and the results changed." "The student graduated and nobody knows how these data were processed." Every data-intensive team has stories like these. The reproducibility crisis is not just a question of academic ethics; first and foremost it is **technical debt**: an analysis that can't be reproduced is worth nothing the moment it is challenged, audited, or handed over.

The good news is that the cure is cheap. Below is the complete recipe, organised so that each layer prevents one class of accident.

## Layer 1: Scripting — erase all traces of manual work

**The accident**: "I remember deleting a few rows in Excel back then…"

The iron rule: **raw data are frozen and read-only; no manual step is allowed anywhere between the raw data and the final charts.** All cleaning, transformation, modelling, and plotting is code. The test: delete every intermediate file and rebuild everything from the scripts.

Supporting habits: a templated project directory (`data-raw/` (read-only), `R/`, `output/`), and relative paths with the `here` package (absolute paths are why projects die when you change computers).

## Layer 2: Git — a time machine for your project

**The accident**: `analysis_final_v3_REALLY_final(edited).R`

Git solves version archaeology: one commit per logical change, and any past state can be recovered. Researchers can keep it minimal — just three actions, `add / commit / push`, recover 80% of the value. Pair it with a private repository on GitHub or Gitee and you have solved backup and collaboration at the same time.

Commit discipline matters more than the tool: write *why* you changed something in the commit message ("Fix weight-trimming threshold: the old value made the ESS too low"). You, three months from now, will be the main beneficiary.

## Layer 3: Pin down randomness and the environment — no more Schrödinger's results

**The accident**: "Same code, but his results are different from mine."

Lock down the three sources one by one:

1. **Random numbers**: set `set.seed()` explicitly for every random step (sampling, imputation, simulation, some optimisers). Random numbers in parallel computing are a separate trap: use `RNGkind("L'Ecuyer-CMRG")` or the parallel-safe seeds built into the future framework.
2. **Package versions**: `renv::init()` + `renv::snapshot()` create a lockfile, and `renv::restore()` recreates the environment exactly. Accidents from major package versions changing default behaviour are real (the default contrast coding and aggregation behaviour of some packages have changed).
3. **The system environment**: the lightweight option is to archive `sessionInfo()`; for heavy requirements (audits years later, cluster deployment), use a Docker container to freeze the operating system as well.

## Layer 4: Pipelines — make "rerun everything" a single command

**The accident**: "I changed the cleaning rules but forgot which later steps to rerun…"

Running seven scripts by hand in the right order means that one day you'll get the order wrong or skip a step. The solution is a pipeline tool: the **targets package** declares the dependencies between steps, and when anything upstream changes it works out which downstream steps are affected and recomputes only those. As a by-product, the whole analysis becomes a visual dependency graph — the best process documentation there is.

The simple alternative: a master `run_all.R` script that sources every step in order. There is no incremental computation, but the baseline of "rerun everything with one command" is met.

## Layer 5: Automated tests — from "able to rerun" to "confident to rerun"

**The accident**: you refactored a function, the results quietly changed, and nobody noticed.

Write assertions for the "facts that must hold" (with testthat or a lightweight `stopifnot`):

- Data assertions: sample sizes conserved, IDs unique, weights summing to the population total, proportions within [0, 1].
- Result anchors: core tables match a frozen version (snapshot tests).
- Unit tests for functions: known input–output pairs for the functions you write.

Only with tests can you "refactor boldly and rerun with confidence". Every analysis program we deliver to clients has tests built in — the programs have to be run by non-developers in environments we can't see (a requirement of the "data never leave the building" model), so the tests are a remote guarantee of quality.

## Layer 6: Text and code from one source — automated reports

**The accident**: the numbers in the paper don't match the code output (a transcription error).

Quarto or R Markdown put the narrative and the computation in the same document: every number, table, and figure is generated by a code chunk, and when the data are updated you re-render and every number in the text refreshes automatically. **No hand-typed statistics exist in the report**, so transcription errors go extinct.

## An adoption roadmap (don't try to do it all at once)

- This week: layer 1 (scripting) + layer 2 (Git) — lowest cost, highest return.
- From your next project: layer 3 (renv + seeds) + layer 6 (Quarto).
- Team or long-term projects: layers 4 and 5 (targets + tests).

At first every task takes 20% longer; after three projects you come out ahead because rework drops sharply. Reproducibility isn't a moral burden; it is **an insurance policy for your future self and your colleagues** — and in our line of work, it has become the entry ticket to professional delivery.
