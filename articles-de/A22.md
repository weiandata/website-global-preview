# A22 · R-Paketentwicklung von null bis zur Veröffentlichung: Wie ein Statistikwerkzeug entsteht

## Warum Forschende Pakete schreiben lernen sollten

Jedes Stück Analysecode, von dem Sie dachten, Sie würden es wiederverwenden, steht an derselben Weggabelung: Es verrottet in irgendeinem Projektordner; es wird in sieben leicht unterschiedliche Varianten kopiert; oder – es wird zu einem Werkzeug mit Dokumentation, Tests und Installierbarkeit verpackt.

Der dritte Weg kostet weniger, als die meisten denken (moderne Werkzeugketten haben alle mechanische Arbeit automatisiert), aber der Ertrag wächst mit Zinseszins: **Ein Paket ist die ausführbare Form einer Forschungsmethode.** Es macht Ihre Methode installierbar, überprüfbar und zitierbar und zwingt Sie, Schnittstelle und Annahmen zu Ende zu denken. Im Folgenden der vollständige Weg von null bis zur Veröffentlichung, mit Praxisnotizen aus der Entwicklung unseres Open-Source-Pakets IRTC.

## Phase 1: Gerüst und Minimalversion (ein Nachmittag)

```r
usethis::create_package("mytool")   # Standardgerüst erzeugen
usethis::use_mit_license()          # Lizenz wählen
usethis::use_git()                  # Versionsverwaltung ab dem ersten Tag
```

Die Funktionen nach `R/` verschieben, über jede Funktion roxygen2-Kommentare schreiben (`@param`, `@return`, `@examples`, `@export`), dann:

```r
devtools::document()   # Kommentare → Hilfeseiten
devtools::load_all()   # Zum Debuggen laden
devtools::check()      # Umfassende Prüfung: Ziel sind 0 Fehler, 0 Warnungen
```

`check()` ist Ihr Lehrmeister: Beheben Sie, was es bemängelt, und danach verstehen Sie die Paketstandards. Als einziges Nachschlagewerk genügt Wickhams *R Packages* (kostenlos online).

## Phase 2: Vertrauenswürdig machen (die entscheidende Phase)

**Tests – die Lebensader statistischer Software.**
Das Gefährliche an statistischem Code: Er meldet keinen Fehler, wenn er falsch rechnet, er liefert nur still eine falsche Zahl. Beginnen Sie mit `usethis::use_testthat()` und ordnen Sie die Teststrategie nach Wichtigkeit:

1. **Anker für Korrektheit**: Vergleich mit bekannten Antworten (von Hand gerechnete Kleinbeispiele, Lehrbuchaufgaben, Ergebnisse ausgereifter Software);
2. **Simulationsrückgewinnung**: Daten mit bekannten wahren Parametern erzeugen → schätzen → zusichern, dass die Abweichung innerhalb der Toleranz liegt (der Goldstandard für statistische Methoden);
3. **Grenzfälle und Absicherung**: leere Daten, alles fehlend, eine einzige Zeile, unzulässige Argumente – jeder Fall sollte eine **klare Fehlermeldung** ergeben statt eines rätselhaften Absturzes;
4. **Regressionstests**: Jeder behobene Fehler wird als Test festgeschrieben, damit man nicht zweimal in dieselbe Grube fällt.

Erfahrungswert: Testcode ≥ Funktionscode gilt als bestanden. In der Testsuite von IRTC nehmen Simulationsrückgewinnung und der Abgleich mit anderen Implementierungen den größten Raum ein – das Fundament dafür, dass die Engine „richtig rechnet“.

**Fehlerphilosophie.** Bei ungültigen Eingaben am Ort des Problems in verständlicher Sprache melden („resp enthält negative Werte; die Antwortmatrix muss aus nichtnegativen ganzen Zahlen bestehen“), statt Nutzende durch 20 Ebenen Aufrufstapel graben zu lassen. Situationen jenseits der eigenen Fähigkeiten **ausdrücklich ablehnen**, nie stillschweigend fragwürdige Ergebnisse liefern – „ehrliches Scheitern“ ist die Tugend statistischer Software.

**Vignette.** Die Funktionsdokumentation beantwortet „wie rufe ich das auf“, eine Vignette „für welche Situationen, mit welchem vollständigen Ablauf und wie deute ich die Ergebnisse“. Eine gute Vignette hat oft mehr Reichweite als das Paket selbst.

## Phase 3: Performance (falls Ihr Gebiet sie braucht)

Zuerst auf R-Ebene herausholen, was geht: Vektorisierung, keine wachsenden Objekte in Schleifen, data.table. Reicht das nicht, geht es zu Rcpp:

```r
usethis::use_rcpp_armadillo()
```

Engpassfunktionen (meist Likelihood-Berechnungen, also enge Schleifen) wandern nach C++, R bleibt nur die Schnittstelle. Genau so ist IRTC aufgebaut: Die Schätzengine ist vollständig C++ (einschließlich Multithreading und Streaming-Speicherverwaltung), Nutzende sehen weiterhin eine gewöhnliche R-Funktion. **Grundsatz: erst messen (Paket profvis), dann optimieren – Optimierung nach Gefühl liegt in neun von zehn Fällen daneben.**

## Phase 4: Veröffentlichung

**Veröffentlichung auf GitHub (am selben Tag machbar):** ins Repository pushen + README (ein kurzer Absatz, welches Problem das Paket löst, + Installationsbefehl + Minimalbeispiel) + CI über GitHub Actions (`usethis::use_github_action("check-standard")`, automatische plattformübergreifende Prüfung). Danach lässt sich das Paket über `remotes::install_github()` installieren – bereits eine ordentliche Open-Source-Veröffentlichung.

**Einreichung bei CRAN (optionaler Schritt für Fortgeschrittene):** Der Gewinn ist das vertrauenswürdige Gütesiegel und die Reichweite von `install.packages()`. Zusatzarbeit: Einhaltung der Richtlinien (Laufzeitgrenzen für Beispiele, keine Schreibzugriffe auf die Festplatte der Nutzenden, vollständige Dokumentation), plattformübergreifende Vorprüfungen (`devtools::check_win_devel()`, rhub) und Erläuterungen in `cran-comments.md`. Die Prüfung erfolgt von Hand, und eine Ablehnung beim ersten Versuch ist normal – Punkt für Punkt beheben und erneut einreichen. Haltung: Die Prüfenden helfen Ihnen, Veröffentlichungsqualität zu erreichen.

**Zitation und Urheberschaft:** Eine Datei `inst/CITATION` anlegen, damit Nutzende Autor und Quelle in ihren Arbeiten automatisch zitieren können – der langfristige Ertrag wissenschaftlicher Werkzeuge kommt von hier.

## Zeitbudget als Orientierung

Minimalversion in 1 Tag; vertrauenswürdige Version mit Tests und Vignette in 1–2 Wochen (nebenbei); Feinschliff auf CRAN-Niveau noch einmal 1–2 Wochen. Verglichen mit der Entwicklung der Methode selbst ist das Verpacken ein kleiner Bruchteil, bestimmt aber den **Überlebensradius** der Methode: Skripte in einem Ordner überleben das Projekt nicht, ein Open-Source-Paket mit Tests und Dokumentation kann viele Jahre leben.
